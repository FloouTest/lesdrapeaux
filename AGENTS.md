# AGENTS.md

Instructions for coding agents working in **Atlas des Drapeaux**.

## 1. Project summary

Atlas des Drapeaux is a French-language geography quiz covering flags and capitals. It supports:

- casual quizzes (free-text and multiple choice),
- ranked play with divisions, streak bonuses, and daily limits,
- global leaderboards and player history,
- real-time-ish multiplayer Versus rooms,
- local pseudo/account persistence,
- a standalone administration page.

The stack is deliberately small:

- React + Vite frontend,
- plain JavaScript/JSX (no TypeScript application code),
- Cloudflare Pages Functions under `functions/api/`,
- Cloudflare D1 / SQLite persistence,
- Vitest + Testing Library for frontend tests,
- Node's built-in test runner and Miniflare for backend tests.

All user-facing copy is French. Keep new interface text in French unless explicitly asked otherwise.

## 2. Before changing anything

1. Run `git status --short --branch`.
2. Treat every pre-existing modification as user work. Never reset, overwrite, stage, or reformat unrelated files.
3. Read the full target component and its nearby tests/styles before editing.
4. Trace both sides of API-backed features: the React caller and the matching Pages Function.
5. If a change affects persisted data, read `schema.sql`, all relevant migrations, and backend tests first.
6. Prefer a focused change over broad cleanup. Opportunistic refactors are welcome only when they are behavior-preserving and tightly related.

Never read, print, commit, or expose secrets from `.env`. The file is intentionally not documentation.

## 4. Important development warning

`npm run dev` serves the frontend locally, but Vite proxies `/api/*` to:

```text
https://lesdrapeaux.pages.dev
```

That is the production API and production D1 database. Avoid manually exercising mutating flows against the default proxy unless the user explicitly accepts production data changes.

To use a local Pages runtime or another safe backend:

```bash
VITE_API_PROXY=http://127.0.0.1:8788 npm run dev
```

`VITE_API_PROXY` must be an origin; Vite preserves the `/api/*` path. There is currently no committed Wrangler configuration, so do not assume `wrangler pages dev` is preconfigured.

## 6. Frontend architecture

### Navigation

There is no router library. `src/App.jsx` owns a string-valued `screen` state and conditionally renders screens. Navigation callbacks generally call `setScreen(...)`.

Current screens include:

- `account`
- `home`
- `quiz`
- `results`
- `leaderboard`
- `history`
- `versus`

Versus invitations are the exception: `?room=CODE` is read from `location.search`, and Versus updates browser history directly. Preserve invitation behavior when touching initialization or navigation.

### Core quiz flow

1. `Home` chooses a category/mode or starts ranked play.
2. `Setup` builds a quiz configuration.
3. `App.start()` stores configuration and opens `Quiz`.
4. `Quiz` evaluates answers and returns a result/log through `finish`.
5. `App.finish()` posts casual results to `/api/leaderboard` or ranked results to `/api/ranked`.
6. `Results` displays the final state and replay options.

Casual score submission is intentionally best-effort: an API failure must not prevent local result display. Ranked submission also supplies a fallback result when offline.

### Data and answer matching

- Country definitions come from `src/data/countries.js`.
- Capital mappings come from `capitals.js`.
- Keep flag and capital categories separate (`flags` / `capitals`).
- `src/game.js` owns normalization, typo tolerance, aliases, shuffling, time formatting, and the common `api()` wrapper.
- Preserve accent/punctuation tolerance and aliases when changing answer logic.
- Versus has backend normalization in `functions/api/versus/_shared.js`; frontend and backend behavior may differ intentionally. Test both when changing shared answer semantics.

### Browser persistence

Known local storage keys include:

- `local:pseudo` (current pseudo),
- legacy `pseudo` fallback,
- `quiz-drapeaux-theme` (current theme),
- legacy `theme` fallback,
- `local:weekly_streak`,
- category-specific ranked fallback keys such as `local:ranked_local_flags`.

Maintain backward-compatible reads unless explicitly removing a migration path. Category-specific progression must remain isolated.

### React conventions

- Use function components and hooks.
- Keep network state explicit (`loading`, `ready`, `error`) where users need feedback.
- Cleanup timers, animation frames, polling, and `AbortController`s in effects.
- React Strict Mode is enabled; effects must tolerate setup/cleanup/setup during development.
- Extract pure helpers when logic is testable independently.
- Use semantic HTML and accessible names/roles. Prefer Testing Library role/name queries over implementation selectors.
- Avoid adding dependencies for small utilities that are easy to implement locally.

## 7. Styling and UI conventions

The visual language is an atlas/paper theme using Fraunces headings and compact modern controls.

- Use variables from `src/styles/tokens.css`; do not scatter hard-coded theme colors.
- Every new surface must work in both light and `[data-theme="dark"]` themes.
- Prefer existing tokens: `--paper`, `--paper-2`, `--card`, `--input`, `--ink`, `--muted`, `--teal`, `--coral`, `--gold`, `--line`, `--select`, `--ok`, and `--ko`.
- Reuse existing shared components and class patterns where practical.
- Scope feature-specific selectors with a feature prefix (`history-`, `versus-`, `lb-`, etc.).
- Put broad/shared component styles in `components.css`; feature-specific styles in `features.css`; tokens only in `tokens.css`.
- Add responsive treatment for narrow screens. Existing principal breakpoints are around 640px and 520px.
- Avoid layout changes that cause question/answer controls to jump unexpectedly.
- Preserve visible focus behavior, readable contrast, and disabled states.
- Use emoji as decoration only when appropriate; mark decorative icons `aria-hidden="true"`.

For visual changes, validate the real rendered UI at desktop and mobile widths when browser tooling is available. Also check dark theme.

## 8. API conventions

Frontend requests should normally use `api()` from `src/game.js`, which:

- prefixes paths with `/api/`,
- parses JSON,
- throws on non-2xx responses or `{ ok: false }`,
- uses the server's French `error` message when available.

Pages Functions export method-specific handlers such as:

```js
export async function onRequestGet({ request, env }) {}
export async function onRequestPost({ request, env }) {}
```

Response conventions:

- JSON body,
- `{ ok: true, ... }` for success,
- `{ ok: false, error: "Message français." }` for failure,
- appropriate HTTP status (`400`, `401`, `403`, `404`, `409`, `500`, etc.),
- `Content-Type: application/json; charset=utf-8`,
- `Cache-Control: no-store...` for private/live state.

Validate and bound all browser input on the server. Existing common limits include 20-character pseudos and bounded room codes. Never trust score, category, room, token, or index fields from clients.

### Endpoint groups

- `/api/account/*`: claim, login, account status. Passwords use Web Crypto PBKDF2-SHA256 with random salts and constant-time comparison.
- `/api/leaderboard`: casual score write/read.
- `/api/history`: merged casual/ranked player history.
- `/api/ranked`: apply ranked result.
- `/api/ranked/player`: player progress.
- `/api/ranked/leaderboard`: ranked standings.
- `/api/versus/*`: create, join, start, state polling, answer.
- `/api/admin/*`: protected settings/history/player/reset operations.

Shared backend helpers belong in each domain's shared module. Note Cloudflare routing behavior: underscore-prefixed modules are intentionally non-routes in ranked and Versus. Account's shared module deliberately lacks an underscore for its current bundling/import behavior; do not rename it casually.

## 9. Versus invariants

Versus is polling-based and security-sensitive. Preserve these rules:

- Room codes exclude ambiguous characters.
- Player tokens identify participants and must not leak to other players.
- Correct answers and aliases stay server-side; only MCQ choices may be public.
- Players have independent question indexes and HP.
- Answer submission must guard against replaying old indexes.
- A player cannot answer after elimination or room completion.
- Only the host may start a room.
- Room capacity supports up to eight players.
- D1 has limits that differ from generic SQLite. Keep `tests/versus-d1.test.mjs` for runtime compatibility.
- Poll effects need cancellation and should back off after errors.
- Feedback timing should not unnecessarily block rendering the next question.

Versus tables are created lazily by `ensureTables()`. Extra settings/options tables avoid destructive assumptions about already-deployed room schemas.

## 10. Ranked and history invariants

- There are 13 ranked divisions indexed `0` through `12`.
- Promotion occurs every 100 FP.
- A score of at least 80% continues the streak.
- Daily reset uses the `Europe/Paris` calendar date, not raw UTC.
- Daily limit is stored in `settings` and falls back to `5`.
- Flags progression uses the legacy `players` table.
- Capitals progression uses `ranked_players` and must remain independent.
- Casual and ranked rows are merged for player history.
- Existing flag records predate category support and default to `flags`.

When changing point calculations, promotions, streaks, or daily limits, add direct tests for boundary conditions.

## 11. Database rules

`schema.sql` is for fresh installs. Existing deployed databases require additive migration files.

Never tell an operator to re-run `schema.sql` as an upgrade. For schema changes:

1. Update `schema.sql` for fresh installations.
2. Add a new idempotent or clearly one-time `migration_vN_description.sql` for existing installations.
3. Preserve existing data and defaults.
4. Add indexes for new common filters/orderings.
5. Test both fresh-schema behavior and migration from the previous shape.
6. Update `DEPLOIEMENT.md` with the exact remote migration command.

D1 binding name is `DB`; backend code expects `env.DB`.

## 12. Testing expectations

### Frontend/unit tests

`npm run test:unit` runs Vitest in jsdom over `src/**/*.{test,spec}.{js,jsx,ts,tsx}`. Setup is in `src/test/setup.ts`.

- Put tests beside source files.
- Test pure calculations directly.
- Test user-visible React behavior with Testing Library.
- Mock `fetch` explicitly and restore globals/spies after each test.
- Clear local storage and URL state where tests depend on them.
- Prefer deterministic time/randomness via mocks.

### Backend tests

`npm run test:backend` runs:

- `tests/versus.test.mjs`: Node test runner with an in-memory SQLite-compatible D1 adapter.
- `tests/versus-d1.test.mjs`: Miniflare D1 tests for real runtime constraints.

For API changes, test status code and response body. For SQL mutations, assert persisted rows—not only returned JSON.

### Minimum validation matrix

For most changes:

```bash
npm run test:unit
npm run build
git diff --check
```

For any function, API, SQL, ranked, leaderboard, history persistence, account, or Versus change:

```bash
npm test
npm run build
git diff --check
```

Also run Prettier check/write on changed source files. Do not claim success without reporting commands actually run.

## 13. Security and privacy

- Never expose password hashes, salts, admin secrets, player tokens, or hidden quiz answers.
- Use parameterized D1 statements (`prepare(...).bind(...)`), never concatenate user data into SQL.
- Keep authentication and authorization checks server-side.
- Preserve constant-time password hash comparison.
- Avoid logging credentials, request authorization headers, or complete private payloads.
- Keep private and mutable API responses uncached.
- Do not weaken validation merely to make a frontend flow pass.

## 14. Admin page

`admin.html` is a standalone Vite entry, not a React component. It contains its own markup, styles, and script. Changes there do not automatically inherit React styles or helpers.

When touching admin behavior:

- test the separate `/admin.html` build output,
- preserve API authentication headers,
- keep user-facing admin errors in French,
- avoid duplicating backend authorization rules in place of server checks.

## 15. Deployment

Cloudflare Pages settings:

- build command: `npm run build`
- output directory: `dist`
- root directory: repository root
- D1 binding: `DB`

Vite builds both `index.html` and `admin.html`. Cloudflare discovers `functions/` from the repository root.

Database commands in deployment docs use the `flags-quiz-db` name. Remote migrations are destructive operational actions: never run them without explicit user authorization and confirmation of the target environment.

## 16. Definition of done

A task is complete when:

- requested behavior works,
- relevant edge cases are covered,
- loading/error/empty states remain coherent,
- mobile and dark theme are considered for UI changes,
- API input remains validated,
- existing persistence compatibility is preserved,
- targeted tests pass,
- required broader tests pass,
- production build succeeds,
- formatting and `git diff --check` pass,
- final response lists changed files and validation performed.

Keep final reports concise. Mention unresolved risks or tests that could not run.
